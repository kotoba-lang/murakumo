# File-size limit diagnostic and crash-report side effect

On 2026-11-03 at approximately 09:07 UTC, an experimental `pr-submit` command added `LimitFSIZE=4M` alongside `LimitAS=128M`. This was a diagnostic candidate only; the `LimitFSIZE` change was removed from the application source. A local native source-unity emitter used the candidate function with stubbed config/spawn. Its command ran against a task-owned synthetic Unix-domain HTTP peer on Xavier. A small response completed, and its unit and task directory were removed.

A second task-owned test served a 4,259,840-byte response. The emitted systemd oneshot started; systemd showed `LimitFSIZE=4194304`. The output file stopped at 4,194,304 bytes, the curl unit became `failed` with `Result=core-dump`, and no complete response was accepted by the test. The test stopped and reset only its unique unit and checked `LoadState=not-found` / `ActiveState=inactive`; its peer and temporary task directory were removed. This is an isolated synthetic test, not actual inference or a full resident execution.

A subsequent read-only inspection found a 353,642-byte Xavier crash report at `/var/crash/_usr_bin_curl.1000.crash`; its metadata contained a unique `awai156-native-...` task path and this test's localhost/Unix-socket invocation. The report was retained, not deleted or copied. No pre-test inventory of that report path was recorded, so this evidence does not establish whether the path existed beforehand. Its contents were not published. The host's `core_pattern` pipes crashes to apport. The [Linux man-pages documentation](https://www.kernel.org/pub/linux/docs/man-pages/book/man-pages-6.03.pdf) describes `RLIMIT_CORE` behavior for piped core handlers, so merely adding `LimitCORE=0` was not considered sufficient evidence that an oversized response cannot generate another report. No second signal-triggering trial was run.

The experiment demonstrates that a bare file-size limit is not a complete disk-protection solution here. An eventual bounded-output transport must handle oversize safely, preserve fail-closed replay behavior, account for host crash-report policy and aggregate storage, and be tested against an unbounded/chunked peer. Neither a task-only crash nor this test qualifies a governor. `fixture.kotoba`, `normal.py` and `large.py` are diagnostic evidence only; the large test can generate another host crash report and should not be rerun on a shared host. The test-only scripts use temporary paths which require adaptation.
