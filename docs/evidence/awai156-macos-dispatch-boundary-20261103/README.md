# Mac mini dispatch boundary observation

The current `profile_recovery.kotoba` uses fixed `/usr/bin/systemctl` calls to determine the user unit's state and `/usr/bin/systemd-run` to submit the bounded curl task. Its current path is a Linux/systemd controller path, even when its inference endpoint uses a local Unix socket. It is not evidence of a Darwin resident dispatch implementation.

At approximately 08:46 UTC on 2026-11-03, a read-only Tailscale/SSH inspection used batch authentication, strict host-key checking, six-second connect timeouts and at most three concurrent SSH calls. Naphtali, Judah, Zebulun, Levi, Joseph, Issachar, Dan, Benjamin and Asher each reported `/usr/bin/systemctl` and `/usr/bin/systemd-run` not executable/present, while `/bin/launchctl` was executable. Tailscale reported Simeon offline at that sample, so its paths were not checked. No service was started, changed or stopped. The tests do not exclude alternative installations or a separate Linux controller; they apply only to the fixed paths used by this candidate.

A Darwin host boundary or a separately qualified Linux controller with authenticated Mac inference transport must provide the same durable dispatch, status, timeout, duplicate refusal and recovery contract. Existence of launchctl alone is insufficient: see [the launchd lock escape observation](https://github.com/kotoba-lang/murakumo/blob/codex/awai152-process-lifetime-evidence/docs/evidence/awai152-launchd-lock-escape-20261103.json) for an escaped descendant after parent termination. Qualify workload lifetime and resource admission before deployment. Tracked by [AWAI-156](https://linear.app/kotobalabs/issue/AWAI-156), dependent on AWAI-151 and AWAI-152.

A later read-only check at approximately 08:48 UTC saw Simeon online and obtained the same result using strict SSH host-key checking: both fixed systemd paths were absent and `/bin/launchctl` was executable. This completes the path observation for all ten minis; it does not qualify launchd or any workload boundary.

The Linux node Xavier was Tailscale-online at the second check, but batch SSH with strict host-key checking returned host-key verification failure. No trust exception was added and its systemd user manager, available resources and connection to the Mac inference endpoint remain unobserved. This does not establish that Xavier cannot act as a controller once its identity and suitability are independently verified.
