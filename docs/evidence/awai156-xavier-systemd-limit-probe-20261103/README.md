# Xavier systemd user-unit limit observation

On 2026-11-03 around 08:56 UTC, several separately named, task-owned, short-lived diagnostic user units were submitted on Xavier (Linux ARM64, systemd 245) over SSH with strict host-key checking against Tailscale-advertised peer keys. Each ran only `/usr/bin/sleep 3`; no model, network client or existing service was run or changed. The units had unique random names, a five-second timeout, and collection enabled. Simple units disappeared after natural exit. The oneshot unit used `RemainAfterExit=yes`; after it finished, the test stopped only its own exact unit and verified `LoadState=not-found` and `ActiveState=inactive`.

For the oneshot case, the request matched important settings in the resident adapter: `Type=oneshot`, `RemainAfterExit=yes`, `NoNewPrivileges=yes`, `MemoryMax=128M`, and `CPUQuota=25%` (the diagnostic used a shorter five-second start timeout and `sleep` instead of curl). `systemd-run --no-block` returned 0 and `systemctl show` reported `MemoryMax=134217728` and `CPUQuotaPerSecUSec=250ms`. While the test process was alive, the observer checked its command name and compared its `/proc/<pid>/stat` start time before and after reading its cgroup membership and limits.

The process's CPU cgroup and its inspected ancestors had `cpu.cfs_quota_us=-1` and period 100000. Its memory cgroup and three inspected ancestors all had `memory.limit_in_bytes=9223372036854771712`, the near-maximum value seen for an unbounded v1 memory limit, rather than 128 MiB. A separate simple-unit probe requested 64 MiB and CPU 25%, observed the corresponding systemd properties, and observed the same unrestricted process cgroup values. The oneshot process was not made to exceed either requested limit, so this is evidence from kernel configuration, not an empirical stress or OOM test. It concerns this host, user manager, kernel, processes and time only.

Systemd's property readback is therefore insufficient evidence of the requested CPU or memory restriction on this candidate. The current resident adapter's `MemoryMax` and `CPUQuota` settings must not be treated as a qualified resource boundary on Xavier without a working cgroup configuration and an independent enforcement test. Existing unrelated failed units were not modified. The test does not validate GPU memory, all descendants, actual curl or inference, GitHub, transport authentication, admission or a complete governor.

The scripts are diagnostic-only Python observers; they are not production tooling.
