# MLX memory-limit diagnostic on one mini

On 2026-11-03, a strict-host-key, batch-mode SSH diagnostic ran on Issachar, a 16 GiB Apple Silicon Mac mini. In its own short-lived Python process with CPU limit 10 seconds and bytecode writes disabled, the installed MLX 0.29.3 reported `Device(gpu, 0)`. After setting `mlx.core.set_memory_limit` to 4,194,304 bytes, the process evaluated a synthetic float32 array of 16,777,216 bytes and reported 16,777,228 bytes of active MLX memory. It exited 0. The parent imposed a 12-second timeout and collected the child; SSH exited 0. No real model was loaded, and no existing service or persistent setting was changed. The observer script SHA-256 is `7064b0a51f87184314de7b5b8e6e189fad7f66c5295d27fec2a433b51af93802`.

This single bounded observation confirms that this process/version can exceed the requested value. The [current MLX `set_memory_limit` documentation](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.set_memory_limit.html) calls it a guideline rather than a strict cap. The documentation is for 0.32.4; the live mini ran 0.29.3, so the result is separately versioned. `set_wired_limit` controls a different residency setting and is not established here as a hard total-process or host limit. Do not use either setting as proof of governor admission, cross-process isolation or resource reservation.

The test is Python observation of an existing MLX installation, not operational tooling or a selfhost inference implementation. It does not verify larger allocations, external allocation paths, other nodes or versions, long-running inference, process-tree containment or behavior under pressure. The governor still needs a qualified workload and host-level resource boundary.
