# Dedicated QA resident

`resident serve-qa` starts one OpenAI-compatible text endpoint in a dedicated
process. The fixture transport is HTTP on `127.0.0.1`. The process starts no
fleet services or backend probes and writes no state. The one request slot is
held in memory until the request finishes or is aborted. The `resident serve`
and `up` commands retain their fleet behavior.

## Synthetic launch and verification

Run the fixture from the repository root with the existing `kbb --backend sci`
tooling and resolved repository dependencies. The fixture starts a stub backend,
chooses a free loopback port, provisions synthetic authentication in a temporary
directory, and launches the same `resident serve-qa --config FILE` entry point.

```sh
MURAKUMO_TEST_SOURCE=1 node --test --test-concurrency=1 \
  test/qa_resident_test.mjs test/fleet_resilience_test.mjs
```

To build and verify a release candidate, install the pinned `release/`
dependencies with `npm ci --prefix release` and build with `npm run
release:node`. Omit `MURAKUMO_TEST_SOURCE=1` to run the fixture against the
bundle. Check `release/node.sha256` against the exact bundle under test.

For a manual run with a stub, use an isolated working directory with a dedicated
`qa.json` file. Choose either the bundle or the source entry point.

```sh
repo=/absolute/path/to/murakumo
cd /path/to/qa-dir
node "$repo/release/node.mjs" resident serve-qa --config "$PWD/qa.json"
```

```sh
kbb --backend sci --classpath "$repo/src" "$repo/scripts/resident.cljk" \
  serve-qa --config "$PWD/qa.json"
```

The dedicated JSON config accepts exactly the fields below. The example uses
placeholders for values generated by the fixture and illustrative ports.

```json
{
  "bind": "127.0.0.1",
  "port": 8799,
  "backend": "http://127.0.0.1:18096",
  "model": "synthetic-model",
  "auth": {
    "token-sha256": "<lowercase SHA-256 hex of the bearer string>",
    "expires-at-ms": "<integer Unix milliseconds>"
  }
}
```

Both ports must be explicit and different. The backend is an IPv4 loopback
origin with no path, credentials, query or fragment. The listener reports its
mode and bound address after startup. Startup rejects missing, invalid, or
unexpected fields with a `QA config:` diagnostic and exits before listening.

## Client contract

Send `POST /v1/chat/completions` to the dedicated listener, with the exact
configured `model` and a nonempty `messages` array. The corresponding OpenAI
client base URL is `http://127.0.0.1:PORT/v1`. The endpoint accepts text messages,
text content parts, and assistant tool call messages with null content. It
forwards the parsed chat JSON, including tools, tool results, `response_format`,
`stream`, and `stream_options`, to the fixed backend chat path without caller
headers. JSON and SSE bodies are streamed back unchanged. Usage is included
when the backend provides it, including in an SSE usage event. Backend
redirects, retries, and alternate routes are disabled.

Each request must supply one `Authorization` header with the Bearer scheme and
64 lowercase hexadecimal characters generated from 32 CSPRNG bytes. The
config holds the fixed-size SHA-256 digest of that ASCII bearer string and the
wall-clock expiry. The verifier compares the digests in constant time and
checks both the wall-clock deadline and the monotonic deadline established at
startup. The draft allows up to one hour of remaining validity at startup.
Rotate by replacing the digest and expiry and restarting the dedicated process.
Keep bearer values out of configuration files, command-line arguments, and logs.

The resident limits request bodies to 2 MiB. Header and request receive
timeouts are 10 and 30 seconds. Backend forwarding has an eight-minute
deadline covering the response stream. Errors generated by the resident use
`{"error":"<code>"}`.

| HTTP | Code | Condition |
| --- | --- | --- |
| 400 | `qa_text_messages_required`, `qa_invalid_request` | Missing or unsupported messages, malformed JSON, or incomplete request |
| 401 | `unauthorized` | Missing, malformed, duplicate, wrong or expired bearer |
| 404 | `not_found` | Other method or path |
| 413 | `qa_body_too_large` | Request exceeds the size limit |
| 422 | `qa_model_mismatch` | Model differs from the configured ID |
| 429 | `qa_busy` | A request already holds the slot |
| 502 | `qa_backend_unavailable`, `qa_backend_response` | Connection failure, non-success backend status or unsupported response |
| 504 | `qa_backend_timeout` | Backend deadline elapsed before response headers |

If forwarding fails after response headers, the resident terminates the stream.
The client should treat a truncated stream or missing backend completion marker
as a failure. The listener has no fleet execution, discovery, health, or slot
inspection endpoints.

## Apple Silicon acceptance

Plain host-visible TCP loopback is for synthetic verification. Another process
on the host could bypass bearer verification by contacting an unprotected
llama.cpp port directly. A real run requires confinement of both hops to the
authorized principals and an observed direct-access denial from a different
local identity. An IPC proxy in front of a still-reachable TCP backend leaves
the bypass open.

This draft supports IPv4 loopback TCP. Node can make HTTP requests through a
pathname Unix socket via `http.request` and `socketPath`. To select that design,
Node Ops first needs to confirm the pinned llama.cpp build can receive HTTP over
a protected pathname socket and verify the connecting UID/GID, or demonstrate
equivalent isolation that prevents a separate local identity from reaching the
backend. It also needs the owner decision on host, issuer, Agent identity,
credential handoff and storage, operational TTL, and stop procedure. The draft
one-hour cap is a startup validation limit pending that operational decision.

The candidate backend is `inkling-2-mini-gyomu-qa` on naphtali, with IQ1_S,
context 768 and parallelism 1. Port 18096 for the backend and 8799 for the Agent
compat listener are candidates. After the boundary is qualified, Node Ops #296
via Kanji #293 can pin and record the resident, backend, and native Agent
versions and rerun the positive and negative cases on Apple Silicon. Record the
Inkling draft from the native Agent profile, followed by Hiring import,
approval, persistence, and export, separately from the fixture results.
