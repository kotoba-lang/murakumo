# CLIP tokenizer on non-ASCII prompts (stage M slices 41 to 43 and 47, JUN-927)

Recorded 2026-11-07T00:45:25+0900, M1 Max, load average 11.93 12.51 12.15. Programs: `bench/kernels/clip-tokenizer-metal/` (standalone) and the tokenizer inside `bench/kernels/pipeline-metal/pipeline_metal.kotoba.in`; oracle: Hugging Face `CLIPTokenizer` (transformers 5.4.0, the files ComfyUI ships in `comfy/sd1_tokenizer`).

The Kotoba tokenizer used to refuse any non-ASCII byte, so a Japanese prompt could not be rendered at all. It now decodes UTF-8, lower-cases, classifies each code point (whitespace, letter, number, other) the way the oracle's pre-tokenizer does, and runs byte-level BPE over the UTF-8 bytes mapped through GPT-2's `bytes_to_unicode`. The vocabulary and merge loaders previously dropped every entry containing a non-ASCII byte (vocab 47,071 of 49,408, merges 46,881 of 48,894); they now load all of them.

What it supports: ASCII, Latin-1, Latin Extended-A (except U+0130), common symbols, emoji, CJK ideographs, kana, Hangul, fullwidth and halfwidth forms, and the whitespace of the Unicode White_Space property. Anything else is refused, not tokenized differently.

Found by the oracle, not assumed: the transformers 5 tokenizer NFC-normalizes (a letter plus a combining accent becomes one token), and its whitespace is the White_Space property, not `str.isspace` (U+001C to U+001F are ordinary characters). U+2E2F is a letter, which the corpus caught.

NFC (slice 42): a letter followed by exactly one combining mark (U+0300 to U+036F, U+3099, U+309A) is now composed with a table generated from `unicodedata.normalize("NFC")` over every supported lower-case letter whose composition is also supported (155 pairs; the base is lower-cased first, which commutes with composition for these letters). This covers decomposed Japanese (か + U+3099 for が, as macOS file names and some input methods produce) and decomposed Latin accents. The corpus gained every pair that composes, with the base in both cases, and mixed lines: 17,988 lines in all, equal to the oracle. A mark that does not compose with the character before it, two marks in a row (NFC would reorder or build a character outside the supported set), and a leading mark are refused; U+2329, U+232A and U+2ADC (NFC singletons and exclusions) are still refused. A mutant that stops composing is detected (254 lines differ), as are three more refusals. The render-program gate prompt now contains decomposed é and が; ids are exact in both layouts and the image agrees as before (1.7e-2 hf, 1.6e-2 single-file); I read the clean-run line of that gate, not its final verdict line (the digest, write and swap checks printed as before).

Slice 43, same day: two items the older notes listed as open were measured against the oracle. (1) HTML entities: the transformers 5 tokenizer does not unescape them (`&amp;` tokenizes as `&`, `amp`, `;`), so there is nothing to implement; the Kotoba tokenizer already agrees and the line is now in `prompts.txt`. (2) The special-token spellings are real: `<|startoftext|>` and `<|endoftext|>` written in a prompt, in any letter case, become the ids 49406 / 49407 and split the text around them (`a<|endoftext|>b` is `a`, EOS, `b`; `<|endoftext|>'s` keeps the contraction). The Kotoba tokenizer treated them as ordinary text; it now matches them case-insensitively on the input bytes, in both the standalone program and the render program. 10 new lines in `prompts.txt` (variants including a broken spelling, a space inside, a truncated one, and Japanese around one) equal the oracle (39 lines in all), one mutant detected (3 lines differ), the 17,988-line corpus still equal, and the render-program gate passes in both layouts ("gate passed", ids exact).

Slice 47, same day: Greek and Coptic (U+0370 to U+03FF), Cyrillic and its supplement (U+0400 to U+052F), Armenian (U+0531 to U+058A) and the Hebrew letters (U+05D0 to U+05EA) are supported. The class of every code point (the oracle's letter / number / whitespace / other split) and the lower-casing rule are generated from Python's `unicodedata` by `gen_script_tables.py` into packed run tables (31 class runs, 24 lower-case runs; the lower-case delta is stored with an offset of 256 because some Coptic and Greek capitals lower-case to a smaller code point, which the first version of the table got wrong and the corpus caught at U+0373). The NFC table is now generated by `gen_nfc_table.py` and grew from 155 to 210 pairs (Greek tonos and dialytika, Cyrillic й and ё and the others). Refused instead of guessed: marks, anything NFC changes (singletons such as U+037E and U+0387), the capital sigma (it lower-cases to a final or medial sigma by context), unassigned code points. The unicode corpus is now 18,632 lines (every code point of the new ranges, every composing pair), all equal to the oracle; two new mutants (class run end, alternating lower-case rule) are detected (906 and 228 lines differ); the render-program gate prompt now contains Cyrillic, Greek, Armenian and Hebrew words and passes in both layouts (ids exact, ctx 9.3e-3 hf / 6.4e-3 single, nothing else changed). The refusal tests now use Arabic and the capital sigma.

Not done: Greek, Cyrillic, Arabic, Indic and other scripts (refused); NFC beyond one mark after a letter (refused); `embedding:` names; the separate `text-encode-metal` program still has the ASCII-only copy of the tokenizer. The supported-range table was checked against the oracle over the corpus, not against Unicode's database, so a code point inside a supported range that the corpus skipped (the CJK ranges are sampled) is covered only by the range rule.
