# Digest before read: the render program refuses an unpinned checkpoint (stage M slice 37, JUN-927)

Recorded 2026-11-06T22:33:57+0900, M1 Max, load average 9.68 10.17 10.66. Program: `bench/kernels/pipeline-metal/pipeline_metal.kotoba.in`; gates `run.sh` (both layouts) and `big_f16.sh`.

The SHA-256 code of slice 36 is now helpers inside the render program. Before anything else touches the checkpoint, `main` hashes the whole file, reads the pinned digest (the first 64 characters of a digest file whose path is the new `@EXPECT@` parameter) and traps on any difference or unreadable file. The placeholder has no default, so a build without a pinned digest does not compile into a working program.

Follow-up, same day (slice 38): the hash-then-read gap is closed. `main` now opens the checkpoint once, hashes through that descriptor, and every later read (header, tensor data) uses the same descriptor, so replacing the path after the hash (rename over it) cannot change what is read. Test: a mutant renames a 4096-byte file over the checkpoint path right after the digest check; the path then holds the other file (checked by its size), and the render is unchanged from the clean run in both layouts (hf: ids exact, image 1.6e-2; single-file: ids exact, image 1.7e-2). An in-place write after the hash is now detected as well (slice 39): `fstat` stamps (size, modification time in seconds and nanoseconds; macOS arm64 `struct stat` offsets 96, 48, 56) are taken before the hash and compared after the last read of the file, and the program traps on any difference before it renders. Test: a mutant opens the checkpoint for writing after the digest check and rewrites its first byte with the value it already has (contents unchanged, only the modification time moves); both layouts refuse it with no render output, and the clean runs, the swap test and the rest of the gate are unchanged. This catches a modification during the hash-and-load window (the only time the file is read; the weights are in memory afterwards). Slice 40 adds the change time (ctime, `struct stat` offsets 64 and 72) to the stamp, which the kernel sets on any write or metadata change and a program cannot set back, so a writer that restores the modification time is caught too. Test: the same write with size and mtime masked out of the stamp (read as 0) is still refused, by ctime alone, in both layouts; this also checks the ctime offsets.

Correction to the slice-38 test: it reported "render unchanged" after the rename-over, but that line was empty and my pass check treated an empty line as success, so the test was vacuous. It was caught while adding ctime: replacing the path unlinks the hashed file's old name, which changes its ctime, so the stamp check now refuses that run. The swap test now expects exactly that (path replaced by a 4096-byte file, run refused, no render output) and the clean-run check fails on an empty comparison line. Reading through the hashed descriptor remains, but its immunity to a swap is no longer separately tested because ctime catches the swap first.

Prerequisite for these gates: an amu checkout whose `bin/amu compile` accepts `--runtime-profile` (the runs here used a worktree of `kotoba-lang/amu` at 5beb858cf, 2026-11-06). The long-lived `kotoba-lang/amu` checkout on this Mac is a detached HEAD from 2026-10-30, 666 commits behind main, and refuses the flag; I did not move it because it is not mine (it has local `.DS_Store` changes and an owner-chosen position).

What this is and is not: it is the mechanism. The digests in these gates are computed from the fixture by `shasum`, so they prove the program hashes the file it then reads and refuses a different digest. They are not a pin from a source; for a real checkpoint the expected digest has to come from the model's publisher (D1), and until then that artifact stays "unverified" in the AGENTS.md sense.
